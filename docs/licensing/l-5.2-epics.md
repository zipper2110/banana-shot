# L-5.2 Epics: Build Expiry, Version Rules, and Update Check

This file tracks the work of L-5.2 (build expiry, version rules, and update
check). The design is in `build-expiry-spec.md` ("the spec"). The user scenarios are in
`expiry-scenarios.md`.

## How to use this file

- Each epic has a scope, the spec sections, its dependencies, and a list of
  stories.
- Each story has a status, the spec sections, the acceptance criteria, and
  the tests that prove it.
- The acceptance criteria come from the "Tests" section of the spec. If the
  spec changes, change the story too. The spec has priority.
- Do the epics in the order of their numbers. Stories in E2, E3, and E4 do
  not depend on each other, so they can run in parallel.
- Do not remove a story when it is done. Set its status to `done`, and write
  the test classes or the test methods in "Tests".
- One PR can contain one or more stories of one epic. Each PR must pass CI.

Status values:

| Status | Meaning |
|---|---|
| `open` | No work started. |
| `in-progress` | Work started. The story is not complete. |
| `done` | All acceptance criteria pass. "Tests" names the proof. |

Each story has a line `- Status: <value>`. E0-S3 makes the release check
read these lines. Do not change the format of these lines.

The spec forbids a release with only some of the measures (see "Decisions" in
the spec). Thus, do not push a `v*.*.*` tag while a story in this file is not
`done`.

## E1 Build information

Scope: the build date and the version in the code, and the check of the app
image in the release workflow.

Spec: "Build expiry", "Rules for the app" (the places that read the version).

### E1-S1 Generate `BuildInfo.kt`

- Status: done
- Spec: "Build expiry"
- Acceptance:
  - The Maven phase `generate-sources` fills a template and makes
    `BuildInfo.kt` with `const val BUILD_DATE` (`yyyy-MM-dd`, UTC) and
    `const val VERSION` (`${revision}`).
  - The Kotlin compiler compiles the generated folder.
  - No resource file, system property, or `.cfg` entry holds the date or the
    version.
  - `BUILD_DATE` is a valid `yyyy-MM-dd` date. `VERSION` is the version from
    `pom.xml`.
  - Implementation note: some Maven plugins do not replace
    `${maven.build.timestamp}` in a template (MRESOURCES-99). If this
    occurs, copy the value into a property in `pom.xml` (for example
    `<build.date>${maven.build.timestamp}</build.date>`), and use that
    property in the template.
  - "Getting started (development)" in `README.md` tells that IntelliJ does
    not run `generate-sources`, and that `mvn -DskipTests package` is the fix
    for an IDE run in expired mode.
  - The same README section warns that a development run and the installed
    app share the saved time and the flag in the preferences. A manual clock
    test with a development build changes the installed app.
- Implementation: `templating-maven-plugin` 3.0.0 fills
  `src/main/kotlin-templates/org/litvin/license/BuildInfo.kt` into
  `target/generated-sources/kotlin-templates`. The template uses the
  property `build.date` (see the implementation note). The plugin adds the
  folder to the compile source roots, so the Kotlin compiler compiles it.
- Tests: `BuildInfoTest` (`BUILD_DATE` is a valid date and is not in the
  future; `VERSION` is the Maven `project.version`, which Surefire gives as
  `bananashot.test.projectVersion`). A build with `-Drevision=1.2.3` gives
  `VERSION = "1.2.3"` (checked by hand on 2026-10-02).

- Implementation: `AppInfo.version` and `AppInfo.displayName` are

### E1-S5 `Validate-AppImage.ps1` and the release workflow step

- Status: done
- Spec: "Build expiry", "Trust for the HTTPS connection"
- Acceptance:
  - `Validate-AppImage.ps1 -Version <version>` runs `BuildInfoPrinter` with
    `runtime\bin\java.exe -cp "app\*"`.
  - It changes the version as `Build-AppImage.ps1` does (removes a `v` at the
    start and the text after a `-`).
  - It fails in each case of the spec: the class does not run or prints no
    date or no version; the expiry is not 6 calendar months after the build
    date; the build date is more than 7 days ago; the build date is later
    than today plus 1 day; the version is not the jpackage `--app-version`.
  - It reads `JAVA_VERSION` from `runtime\release`. It fails when
    `runtime\bin\java.exe --list-modules` does not contain
    `jdk.crypto.mscapi` or `java.net.http`, or (only for JDK earlier than 22)
    `jdk.crypto.ec`.
  - If a module is missing, `Build-AppImage.ps1` adds it with
    `--add-modules`, with the full list of modules that the app needs.
  - `windows-release.yml` runs the script directly after "Build application
    image", with `APP_VERSION`. `Validate-Release.ps1` stays the first step.
  - The packaged diagnostics do not run these checks.
- Finding of 2026-10-02: with JDK 17, the default jpackage runtime of a
  non-modular JAR contains all modules of the JDK, also `jdk.crypto.mscapi`
  and `jdk.crypto.ec`. Thus, `Build-AppImage.ps1` needs no `--add-modules`
  now. The jpackage of JDK 17 does not expand `ALL-DEFAULT`: it gives a
  runtime with only the named modules. If B-23 (JDK 25) removes a module,
  the script fails, and `--add-modules` must name the full list.
- B-23 (2026-10-03): `Build-AppImage.ps1` now gives `--add-modules` with the
  full list (see B-23 in `backlog.md`). A JDK 25 test image contains
  `jdk.crypto.mscapi` and `java.net.http`.
- Tests: no automatic test (the repository has no tests for the release
  scripts). Checked by hand on 2026-10-02 with Windows PowerShell 5.1, with
  app images that have a jlink runtime of JDK 17 and the app JAR:
  - All modules and a correct version (`v1.2.3`, `1.2.3-rc1`): passes.
  - A different version: fails.
  - No `jdk.crypto.mscapi` and no `jdk.crypto.ec`: fails and names them.
  - No app JAR: fails with the Java error.
  - Build date 8 days ago or 2 days later: fails. 7 days ago or 1 day
    later: passes. Build date `2026-02-30`: fails.
  - Not checked: an expiry date that is not 6 months after the build date
    (only a change of the code can make it), and PowerShell 7 (the release
    runner uses it; it is not installed on the local computer). The first
    release workflow run checks PowerShell 7.

## E2 Version rules model

Scope: the parse and the validation of the rules file, the version
comparison, the saved file, and the file in the repository. Pure code: no
network, no Swing.

Spec: "Version rules file", "Fields", "Valid file", "Rules for the app",
"Release steps" (the repository test).

### E2-S1 Version comparison

- Status: done
- Spec: "Rules for the app"
- Acceptance:
  - Versions compare as `MAJOR.MINOR.PATCH` numbers. The text after the
    numbers is ignored. A missing number is 0.
  - `1.3-SNAPSHOT` is `1.3.0`. `1.2.1-beta` is `1.2.1`. A version that does
    not start with a number is `0.0.0`.
- Implementation: `Version.parse` in `org.litvin.license`. A number that is
  too large for an `Int` is the largest `Int`.
- Tests: `VersionTest`.

### E2-S2 Parse and validate the file

- Status: done
- Spec: "Fields", "Valid file"
- Acceptance:
  - File level: a body larger than 64 KB, a body that is not JSON, a top
    level that is not an object, no `schema` or a `schema` that is not an
    integer, and no `rules` or `rules` that is not a list give "not valid".
  - An empty `rules` list is valid.
  - An integer `schema` that is not 1 gives "unknown schema".
  - Rule level: a rule with no `id`, no `toVersion`, or no `stopsOn`, a
    `stopsOn` that is not a `yyyy-MM-dd` date, or a `fromVersion` that is not
    a string is ignored. Its `id` (if any) goes to the log. The other rules
    apply.
  - Field level: a `message`, `notes`, or `installerUrl` that is not a
    string is ignored, and the rest of the rule or of `latest` applies.
  - A `latest` that is not an object, or with no `version` or no
    `downloadUrl`, is ignored as a whole.
  - Unknown fields are ignored. The known fields are read.
  - Two rules with the same `id` both apply.
- Implementation: `VersionRulesParser.parse` gives `Valid`, `UnknownSchema`,
  or `NotValid`. `Valid.problems` names each rule and each field that the
  parser ignored, and the parser writes each problem to the log. The
  repository test of E2-S5 uses this list.
- Decision: the parser checks `schema` before `rules`. A file with an
  unknown schema can have a different format. Thus, an integer `schema`
  that is not 1 gives "unknown schema" also when `rules` is missing. The
  spec contains this rule ("Valid file").
- Tests: `VersionRulesParserTest`.

### E2-S3 Rules that match the version

- Status: done
- Spec: "Fields", "Rules for the app"
- Acceptance:
  - A rule matches when the app version is in `fromVersion`..`toVersion`
    (both ends included). With no `fromVersion`, the rule matches all
    versions up to `toVersion`.
  - A rule that matches `latest.version` is ignored.
  - A rule for a different version has no effect.
- Implementation: `VersionRule.matches` and `VersionRules.matchingRules`.
- Tests: `VersionRulesTest`.

### E2-S4 Saved rules file

- Status: done
- Spec: "Rules for the app", "Valid file"
- Acceptance:
  - A new valid file replaces the saved file in the data folder.
  - A file that is not valid, or a file with an unknown schema, does not
    replace the saved file.
  - At start, the app validates the saved file with the same rules. A
    damaged saved file gives no saved file, and no error to the user.
  - The data folder is a constructor parameter.
- Implementation: `SavedVersionRules(dataFolder)` keeps the body of the last
  valid file as `version-policy.json` in the data folder. `replaceIfValid`
  writes it through a temporary file and a move. A failed read or write
  goes to the log only. E7-S1 gives the production data folder.
- Tests: `SavedVersionRulesTest`.

### E2-S5 `release/version-policy.json` and the repository test

- Status: done
- Spec: "Release steps"
- Acceptance:
  - `release/version-policy.json` exists, with `schema: 1`, a valid
    `latest`, and an empty `rules` list.
  - A test fails when: the file or a rule is not valid; `latest` is not
    valid; `schema` is not 1; a version text does not start with a number;
    a rule matches `latest.version`; a rule matches the version in
    `pom.xml`; two rules have the same `id`.
  - The test fails for a file with `"schema": 2` and for a rule with
    `toVersion` equal to the version in `pom.xml`.
- Decision: no release exists yet. Thus, `latest.version` is `1.0.0`, the
  first release, with the releases page as `downloadUrl` and no
  `installerUrl`. A development build `1.0-SNAPSHOT` compares as `1.0.0`, so
  it shows no update notice. After the first release, set `installerUrl`
  (E10-S1).
- Implementation: the check is only in the test. The version in `pom.xml` is
  `BuildInfo.VERSION`.
- Tests: `VersionPolicyFileTest`.

## E3 Time engine

Scope: the current time, the saved time, the run time, and the clock
rules. Pure code with a fake clock, a fake counter, and a fake store.

Spec: "Time and the clock" and all its subsections except "Trust for the
HTTPS connection".

### E3-S1 Run time counter

- Status: done
- Spec: "Run time"
- Acceptance:
  - The production counter is `Kernel32.INSTANCE.GetTickCount64()`.
  - If the call fails, the counter uses `System.nanoTime` and writes one log
    line. It shows no error.
  - Tests give the counter through a constructor parameter.
  - A jump of the counter (a sleep) moves the saved time forward, also
    offline with the clock behind.
  - A change of the system clock does not change the run time.
- Implementation: `RunTimeCounter.production()` and `FallbackRunTimeCounter`
  in `org.litvin.license.time`. After a failure, the fallback continues from
  the last value of `GetTickCount64`, so the run time does not jump.
- Tests: `RunTimeCounterTest`; `TimeEngineTest` (`a sleep moves the saved
  time forward also offline with the clock behind`, `a change of the system
  clock does not change the run time`).

### E3-S2 File time probe

- Status: done
- Spec: "File time probe"
- Acceptance:
  - At each expiry check, the probe writes a file in the data folder and
    reads its last-modified time.
  - The system time is the later of the Java clock and the file time.
  - A probe that cannot write or read the file uses the Java clock and shows
    no error.
- Implementation: `DataFolderFileTimeProbe` writes `time-probe` in the data
  folder. `SystemTime.withProbe()` gives the later of the Java clock and the
  file time. `SystemTime.withoutProbe()` gives the Java clock for the minute
  tick, because the tick does not read or write files. `TimeEngine.start()`
  and `TimeEngine.check()` use the probe.
- Tests: `SystemTimeTest`; `TimeEngineTest` (`a file time later than the
  Java clock becomes the system time`, `a Java clock later than the file
  time stays the system time`, `the tick does not use the probe and the
  expiry check does`).

### E3-S3 Saved time calculation

- Status: done
- Spec: "Calculation of the saved time", "Build-date floor"
- Acceptance:
  - The engine keeps the anchor `A` and `C_A`.
    `saved = A + (C(now) − C_A)`.
  - At start: a saved time earlier than the build moment, or no saved time,
    becomes the build moment.
  - Before the first server time: a system time later than `saved` moves the
    anchor to the system time.
  - A system time that moves 10 days forward and then back keeps the saved
    time 10 days ahead, and the run time continues from there.
  - A system clock that moves back does not stop the time: the run time
    still moves it forward.
- Implementation: `TimeEngine`. `TimeEngine.buildMoment()` gives 00:00 UTC
  on `BUILD_DATE`.
- Tests: `TimeEngineTest` (`no saved time becomes the build moment`, `a
  saved time earlier than the build moment becomes the build moment`,
  `before a server time a later system time moves the saved time to the
  system time`, `a system time 10 days forward and then back keeps the saved
  time 10 days ahead`, `a system clock that moves back does not stop the
  time`).

### E3-S4 Clock behind

- Status: done
- Spec: "Clock behind"
- Acceptance:
  - At start, a system time more than 24 hours before the saved time adds
    12 hours to the saved time, at each start.
  - A system time 23 hours before the saved time has no effect.
  - With no saved time and a system time 1 year before the build date, the
    rule adds 12 hours.
  - The engine reports the "clock behind" state for the notice (E6, E8).
- Implementation: `TimeEngine.clockBehind` is true from a start with the
  clock behind until the first server time. E6 decides about the notice.
- Tests: `TimeEngineTest` (`a system time more than 24 hours before the
  saved time adds 12 hours at each start`, `a start that ends with no close
  still uses the 12 hours`, `a system time 23 hours before the saved time
  has no effect`, `with no saved time and a system time 1 year before the
  build date the rule adds 12 hours`, `a server time after clock behind sets
  the saved time and ends the clock behind state`).

### E3-S5 Server time

- Status: done
- Spec: "Time and the clock", "Calculation of the saved time"
- Acceptance:
  - A server time sets the anchor to the server time, with the counter value
    when the response arrived.
  - A server time earlier than the saved time moves the saved time back. A
    later server time moves it forward.
  - After a server time, a system time that moves back, or forward by
    months, does not change the saved time.
- Implementation: `TimeEngine.serverTime(time, counterAtResponse)`. It
  returns the system time minus the server time, for the wrong clock notice
  (E6-S7).
- Tests: `TimeEngineTest` (`a server time earlier than the saved time moves
  the saved time back`, `a server time later than the saved time moves the
  saved time forward`, `the anchor uses the counter value when the response
  arrived`, `after a server time the system time does not change the saved
  time`, `the server time gives the clock error for the wrong clock
  notice`).

### E3-S6 Write the saved time

- Status: done
- Spec: "Time and the clock"
- Acceptance:
  - The engine writes the saved time at each expiry check, every 5 minutes
    of run time, and when the app closes.
  - A session that ends with no close (End task) loses at most 5 minutes of
    run time.
  - A write with no new server time keeps the later of the stored value and
    the new value.
  - The first write after a new server time replaces a stored value that is
    later. After that, a start with no network uses the corrected value.
  - The store is a constructor parameter. The production store uses the
    preferences.
- Implementation: `TimeEngine.start()`, `check()`, and `close()` write the
  saved time. `TimeEngine.tick()` writes it after 5 minutes of run time.
  The start writes too: a start that ends with End task still uses the 12
  hours of "Clock behind". `PreferencesSavedTimeStore` takes a preferences
  node. E7 selects the production node.
- Tests: `PreferencesSavedTimeStoreTest`; `TimeEngineTest` (`the engine
  writes at start, at each expiry check, and when the app closes`, `the tick
  writes after 5 minutes of run time`, `the first tick after a long sleep
  writes`, `a session that ends with no close loses at most 5 minutes of run
  time`, `a write with no new server time keeps the later stored value`,
  `the first write after a new server time replaces a later stored value`,
  `after a server time correction a start with no network uses the
  corrected value`).

## E4 Expiry evaluator

Scope: the effective expiry, the expiry moment, and the start of the
warning. Pure code.

Spec: "Rules for the app", "Expiry moment".

### E4-S1 Effective expiry

- Status: done
- Spec: "Rules for the app"
- Acceptance:
  - The effective expiry is the earliest of the build expiry and the
    `stopsOn` of each matching rule.
  - Cases: build expiry only; a rule that is earlier; a rule that is later
    (no effect); a rule for a different version; a version that is not
    `MAJOR.MINOR.PATCH`.
  - The file can only make the expiry earlier.
- Implementation: `EffectiveExpiry.of(appVersion, rules, buildExpiry)` in
  `org.litvin.license`. A rule with the same date as the build expiry gives
  the expiry, so that its `message` shows. Of two rules with the same date,
  the first rule in the file gives it.
- Tests: `EffectiveExpiryTest` (15 tests, pass on 2026-10-03).

### E4-S2 Expiry moment and warning start

- Status: done
- Spec: "Expiry moment"
- Acceptance:
  - The version works at 23:59:59 UTC on the day before the expiry date. It
    stops at 00:00 UTC on the expiry date.
  - The warning starts exactly 30 × 24 hours before the expiry moment.
  - One function formats the moment in the local time zone with the hour,
    for example "29 March 2027, 16:00".
- Implementation: `EffectiveExpiry.moment`, `warningStart`, `isExpired`, and
  `isWarning`. `ExpiryMomentFormat.format` (English only until B-11).
- Tests: `EffectiveExpiryTest`.

### E4-S3 Log of the rule that gives the expiry

- Status: done
- Spec: "Rules for the app"
- Acceptance:
  - When a rule gives the effective expiry, the log gets the rule `id` and
    the date. This occurs when the effective expiry changes, and when the
    rule stops the version.
- Implementation: `ExpiryLog.record(expiry, now)`. E6 calls it after each
  expiry check. It writes one line when the effective expiry changes, and one
  line when a rule stops the version.
- Tests: `EffectiveExpiryTest`.

## E5 Rules fetcher

Scope: the HTTPS read of the rules file, the server time, the proxy, the
trust stores, and the guard that keeps the tests off the network.

### E5-S3 Read the file and the server time

- Status: done
- Spec: "Version rules file", "Time and the clock"
- Acceptance:
  - The fetcher waits a maximum of 10 seconds. It stops the read at 64 KB.
  - It does not follow redirects.
  - Result types: "no connection" (no network, timeout, TLS error), or a
    server response with a server time and an optional body.
  - A 404, a redirect, a file that is not valid, and a file with an unknown
    schema all give a server time.
  - The server time is `Date` plus `Age`. `Age: 120` adds 2 minutes. An
    `Age` that is not a number, below 0, or above 3600 is ignored.
  - The request sends no user ID and no analytics data.
- Implementation: `RulesFetcher` (the interface for E6), `RulesFetchResult`
  (`NoConnection` or `ServerResponse`), and `HttpRulesFetcher` in
  `org.litvin.license.online`. The 10 seconds are one total limit for the
  connection, the headers, and the body. The body is only for HTTP 200, and
  is at most 64 KB plus 1 byte, so the parser finds a body that is too large.
  `ServerResponse.counterAtResponse` is the counter value when the headers
  arrived, for `TimeEngine.serverTime`. The request uses HTTP/1.1.
  `HttpRulesFetcher.RULES_URL` is the raw GitHub URL on `master` (the
  repository is public, checked on 2026-10-03).
- Decision (2026-10-03, approved by the author): a response with no valid `Date` header is a server
  response with `serverTime = null`. GitHub always sends `Date`, but a proxy
  can remove it. E6 uses the body of such a response, but no server time.
- Tests: `HttpRulesFetcherTest` (a local server with exact headers: a valid

  unknown schema, the 64 KB limit, `Date` plus `Age`, the `Age` limits, no
